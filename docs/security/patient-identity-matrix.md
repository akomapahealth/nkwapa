# Patient Identity Matrix

Generated by `apps/api/src/patients/patient-identity-matrix.spec.ts`. Edit the table in
`apps/api/src/testing/patient-identity-matrix.ts`, not this file.

Two charts for one person is a clinical safety problem, and consolidating the wrong two is a
worse one that cannot be undone from the product. These are the rules that decide which pairs
an operator is shown, and which merges are refused outright.

## Duplicate candidate rules

A pair is scored by summing the weight of every rule it matches, capped at 100. `HIGH` starts
at 70, `MEDIUM` at 40; below that a pair is `LOW`. The weights are chosen so
that no single weak signal reaches `MEDIUM` on its own, but any two of them together do.

| Rule | Match | Weight | Alone | What it looks like |
| --- | --- | --- | --- | --- |
| Same national ID | exact | 100 | HIGH | Two charts registered with the same national ID, under different names. |
| Same name and date of birth | exact | 50 | MEDIUM | The same person registered twice on different days, with no ID either time. |
| Same ID type, last 4 digits, and date of birth | exact | 45 | MEDIUM | Two charts sharing an ID type, its last four digits and a date of birth, but recorded under different names -- typically one chart holding a married name. |
| Same phone number | exact | 35 | LOW | Two unrelated charts reachable on one phone number, which is usually a household. |
| Same email address | exact | 35 | LOW | One email address on two charts, compared without regard to case. |
| Similar name, same date of birth | fuzzy | 30 | LOW | One surname and one date of birth, with a first name spelt two ways by two volunteers ("Kwabena" and "Kwabina"). The only rule that tolerates a difference. |

Every rule compares normalized values exactly, except the one marked fuzzy: it allows a first
name up to 2 edits away, and only once the surname and the date of birth already agree.
Nothing is ever surfaced on a similarity signal alone.

Two weak signals together clear the bar that neither clears alone: a near-identical name on the same birthday, reachable on one phone number scores 65 and reaches `MEDIUM`.

## Merge refusals

Any one of these stops the merge. The preview reports them before an operator commits, and the
merge endpoint re-checks them inside its transaction.

| Refusal | What it means | What to do | How to reproduce |
| --- | --- | --- | --- |
| `SAME_PATIENT` | This is the same chart on both sides | Choose a different chart as the duplicate. | Name the same chart on both sides of the merge. |
| `PATIENT_NOT_FOUND` | One of these charts no longer exists | Reload the chart and search for the duplicate again. | Preview against a chart id that no longer exists, or was deleted mid-review. |
| `CANONICAL_ALREADY_MERGED` | The chart you are keeping has already been merged into another one | Open the chart it was merged into and start again from there, since that is now the surviving record. | Choose a chart that has already been retired by an earlier merge as the survivor. |
| `SOURCE_ALREADY_MERGED` | The duplicate chart has already been merged into another one | Its records already live on another chart. Open that chart to check whether anything is still outstanding. | Choose an already-retired chart as the duplicate. |
| `CROSS_CLINIC` | These charts belong to different clinics | Charts can only be merged inside one clinic. Record the pair in the duplicate review queue and raise it with both clinics. | Pick two charts whose `primaryClinicId` differs. The duplicate queue marks these ineligible. |
| `CLINIC_INACTIVE` | The clinic that owns these charts is no longer active | Reactivate the clinic before consolidating any of its charts. | Deactivate the clinic that owns both charts, then preview. |
| `ALIAS_CODE_COLLISION` | The duplicate chart’s code is already recorded against another chart | Another chart already answers to this code. Ask a system administrator to check which chart is meant to hold it before merging. | Give a third chart a code alias equal to the duplicate chart's own code. |
| `OPEN_PHARMACY_PREFERENCE_CONFLICT` | Both charts have a current preferred pharmacy | End the preferred pharmacy period on the duplicate chart, then preview the merge again. | Leave both charts holding a preferred pharmacy period with no end date. The database permits only one open period per chart, so the merge would violate it. |
| `PORTAL_LINK_CONFLICT` | Each chart is linked to a different app account | Choose which app account keeps access. The other account will no longer be able to open this chart. | Link each chart to a different app account and preview without naming a portal strategy, so the operator has not yet said which sign-in survives. |

## Merge warnings

None of these blocks a merge. They are the consequences worth reading before committing to an
action with no way back.

| Warning | What it means | What to do | How to reproduce |
| --- | --- | --- | --- |
| `PORTAL_ACCOUNT_RETIRED` | One app account will lose access to this chart | Tell the patient which sign-in still works, or invite them again after the merge. | Link each chart to a different app account and name a portal strategy. |
| `PENDING_INVITES_CANCELLED` | A portal invitation that has not been used yet will be cancelled | Send a fresh invitation from the surviving chart after the merge. | Leave an unclaimed portal invitation on whichever chart the invite strategy drops. |
| `WEAK_DUPLICATE_SIGNAL` | These two charts do not look much alike | Compare the two charts field by field before continuing, and stop if anything but the name differs. | Preview two charts that share nothing but a phone number, scoring LOW. |
| `SOURCE_HAS_MORE_HISTORY` | The duplicate chart holds more history than the one you are keeping | Consider merging the other way round, so the fuller chart is the one that survives. | Choose the chart holding fewer visits and measurements as the survivor. |
| `DUPLICATE_PAIR_PREVIOUSLY_DISMISSED` | Someone already decided these are two different people | Check the note left on that decision in the duplicate review queue before overriding it. | Dismiss the pair in the duplicate review queue, then preview a merge of it anyway. |
